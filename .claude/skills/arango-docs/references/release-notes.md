# Release notes

Rules for `release-notes.md` pages, `api-changes.md`, and the Contextual Data
Platform service versions.

## Breaking changes

Before you write a **Breaking** bullet, check the field or endpoint against the
service's previous release tag, not against `main`.

- A field or endpoint that was added and then changed within the same
  unreleased version is not breaking. No customer could have written code
  against it. Describe it as part of the feature bullet, as the API works now.
- To check: find the endpoint's introducing entry in the service's
  `CHANGELOG.md`. If the endpoint is new in the same release block as the
  change, it's not breaking. Comparing the `.proto` or OpenAPI file across the
  tags is the definitive check.
- A rename that mirrors a CHANGELOG rename entry may still be breaking if a
  pre-release could have shipped the old name. Confirm with the service owner
  instead of assuming.

## Names in older entries

Historic entries name what shipped at the time. Don't rename products in old
release notes.

- At the first mention in each older section, add a pointer to the current
  name once: heading `### Retriever (now AutoRAG)` or inline
  "Retriever (now AutoRAG)".
- Links point to the current pages regardless.

## Beta features

Tag beta features in the release notes too, on the section of the feature,
for example `{{< tag "Agentic AI Suite" "Beta" >}}`. Remove the tags when the
feature reaches GA.

## Service versions of a Contextual Data Platform release

The Service versions page is generated by `{{% service-versions %}}`. Don't edit
the page; add data:

1. Save the release's platform config from
   <https://github.com/arangodb/arangodb-platform-config/releases/> to
   `site/data/data_platform/` under its original name (for example
   `AI_Suite.v4.1.0.yaml`).
2. Add a `date` key (for example `date: August 2026`) matching the headline in
   What's new in the data platform. The build fails without it. Leave the rest
   of the file unchanged.
3. Map every new package to its features in
   `site/data/data_platform_services.yaml` (`features:` list with `name` and an
   optional `link` relative to `site/content/`). Unmapped packages get an empty
   Features cell and a build warning.
